# Code review — 2026-07-12

Multi-agent review of the July 9–12 work (prismql: validator dialect support, PIPE_REFERENCE, result equality, the whole web demo; prismql-rust: temporal kernels). 7 finder dimensions, one adversarial verifier per finding.

**25 raw findings, 25 confirmed, 0 refuted.** A zero-refutation rate is itself a smell, so every finding was re-read by hand; several were reproduced live (the /health 500 was triggered; the '(same key)' example was checked against the data — 276 of 283 groups pair *different* keys). Deduplicated, these are ~13 distinct defects: the X-Forwarded-For bypass was found independently by 3 finders, /reload by 2, the local-tz/UTC divergence by 2.

Scope note: nothing here touches the paper's numbers or core engine semantics — the Chicago 372-match result and the IR-equality proofs are unaffected. The two criticals are public-deploy blockers only (not reachable on localhost).


## CRITICAL (2)

### `src/prismql/server/app.py:191` — [?]

**The rate limiter keys on the client-supplied leftmost X-Forwarded-For value, so a visitor can defeat the 60/min limit entirely by rotating a spoofed header.**

evaluate() computes the rate-limit key as request.headers.get('x-forwarded-for','').split(',')[0].strip() and only falls back to request.client.host when no XFF header is present. Behind Railway's proxy every request will carry an XFF header, and the leftmost element is fully attacker-controlled (proxies append, they do not sanitize the client-supplied left side). An attacker sends `X-Forwarded-For: <random-ip>` with a fresh value on each request; every request lands in a brand-new deque bucket, so len(window) is always 0 and _rate_limited never returns True. The only DoS control on /evaluate is neutralized, and it simultaneously makes the known 'hits dict never drops keys' growth unbounded (one new key per spoofed IP → memory exhaustion). This is the single control that bounds findings on /evaluate compute and /evaluate output=file disk writes, so its bypass amplifies both.

### `src/prismql/server/app.py:308` — [?]

**POST /reload is unauthenticated, not rate-limited, and rebuilds every engine from disk (50k-doc chicago corpus) while holding the global state.lock.**

reload() calls state.reload(), which under state.lock does build_engine(...) for every named corpus — for the demo that means re-loading and re-indexing data/chicago.json (50,000 docs / 4 MB) plus fcc on every call. Only /evaluate passes through _rate_limited; /reload has no limiter at all. Any internet visitor runs `while true; do curl -X POST https://host/reload; done`: each call pegs CPU/IO rebuilding the in-memory backends, and because reload() and evaluate() both acquire state.lock, a flood of /reload calls serializes ahead of and blocks all legitimate /evaluate, /schema, and /health work. A single unauthenticated endpoint gives a trivial sustained DoS. On a public deploy this mutating/expensive route should not be exposed (or must require auth and be rate-limited).
